# Review: #8 Projects API and AI draft

> **Verdict:** Approve · **Merge risk:** Medium (writes files from HTTP; sends user text to a model) · **Read time:** ~15 min
> Plan: `.claude/plans/8-dashboard-v2-projects-api.md` · Evidence: `docs/evidence/8.json` · Autonomy: pr

## What and why
Custom benchmarks ("projects") can now be created, read, updated and deleted over the API. They are stored as `benchmarks/custom/<slug>.yaml` and loaded like any other benchmark. A chosen model can also draft a project (cases plus scorers) from a description and pasted examples, and the draft is returned unsaved for you to review. `benchmarks/custom/` was empty because hand-writing YAML is too slow. The Projects page comes next.

## Design decisions
| Decision | Chosen | Instead of | Why |
| --- | --- | --- | --- |
| Storage | YAML in the custom dir (override `MODELCOMPARE_CUSTOM_DIR`), atomic write, cache invalidated | DB | YAML files are already the benchmark source of truth. The override keeps tests and QA out of the repo |
| Paths | Slug `^[a-z0-9-]{1,64}$`, checked before any path work. The resolved path's parent must be the custom dir | Sanitising names | Rules out traversal (`../x`, NUL, symlinks pointing out) |
| Names | 409 on an existing file, a duplicate name (standard or custom), or a reserved name (`standard`, `custom`, dimension dirs). Empty slugified names → `project-<hash>` | Allowing them | A reserved name could never be resolved by name |
| Saved files | `source: custom` forced; `dimension`, `repeats` and `pass_threshold` always written | Dropping defaults | A future default change can't silently alter saved projects |
| Limits | Body streamed and cut at 1 MB (413); bad Content-Length → 400 | Trusting Content-Length | Chunked bodies had no limit |
| Errors | 422 `detail: [{loc: [str…], msg}]` with case positions; other statuses a string (documented in the module docstring) | Mixed shapes | The editor can map errors to fields |
| Draft safety (lead decision) | Drafts never offer or accept a code-running scorer (`code_exec`, `test_quality`). Description and examples sit inside a `<user_data>` block marked as data | Offering every scorer | Those scorers run Python on your machine, and pasted examples are untrusted. You can still add them by hand |
| Draft output | Narrow hand-written JSON schema (inlined, no defaults, no extra keys). `max_tokens` capped at the model's limit. Truncation → clear 422. One retry only if the provider rejects `response_format`. Cost and tokens summed across attempts | `Benchmark.model_json_schema()`; retry on any error | Strict providers reject broad schemas, a blind retry double-charges, and a drafted `repeats: 20` would multiply run cost |
| Access | All projects routes and `/api/scorers` behind the localhost Host/Origin check; API prefix only | Root aliases | `/projects/` is a Next page; these routes write files |

## Risks and findings
Reviewer agent: round 1 requested changes (2 High, 9 Medium, Lows), all fixed. The lead added `test_quality` to the blocked scorers, since it also executes code.
| Sev | Finding | Status |
| --- | --- | --- |
| High | Drafts could include `code_exec` steered by pasted examples (local code execution) | Fixed: code-running scorers blocked; examples fenced as data |
| High | `max_tokens` 8192 exceeded some models' limits; truncation produced a misleading error | Fixed |
| High (lead) | No red runs; blind retry double-charged and lost the first attempt's cost | Fixed |
| Medium | Reserved names, empty slugs, 500s on bad slugs, chunked body limit, schema breadth, error `loc` shape, untested 409/litellm paths, plan deviation | Fixed and recorded in the plan's Delivery notes |

Remaining risks:
- Real-provider structured output (`response_format` rejection text, `finish_reason`) is covered only with fakes.
- `benchmarks/custom/` isn't gitignored, so saved projects show up as untracked files in your checkout (intended: they're your benchmarks).

## How to test for humans

Where: Not on develop yet
Who: the plan doesn't name an account (local, single user)
About 4 minutes. The automated checks passed. This is what a person can judge that those checks do not.

Nothing to click yet; the Projects page comes in the next milestone. With `modelcompare serve` running:

1. Open http://127.0.0.1:8000/api/scorers. You should see the scorer names (exact, contains, regex, llm_judge, code_exec…).
2. Open http://127.0.0.1:8000/api/projects. You should see `[]`, or your saved projects.
3. Optional, costs a little: POST to `/api/projects/draft` with one of your models, a one-line description and two examples.
4. You should see a drafted benchmark with cases and scorers, plus its cost. Nothing appears in `engine/benchmarks/custom/` until you save.
   - Watch for: draft quality. Do the cases test what you described?
